# Developer Integration Guide

How the existing ASP.NET / .NET Framework 4.0 application consumes the `Icegate.Integration`
.NET 8 Web API. The legacy application never talks to ICEGATE directly and never implements
ICEGATE authentication, token management, or multipart parsing - all of that lives in this
API.

## 1. Architecture recap

```
Legacy .NET Framework 4.0 app  --HTTPS/REST-->  Icegate.Integration (.NET 8)  --HTTPS-->  ICEGATE UAT/PROD
```

The legacy app authenticates to **our** API with an internal API key (`X-API-KEY`), separate
from and unrelated to any ICEGATE credential. Our API authenticates to **ICEGATE** using the
token lifecycle described below - the legacy app never sees an ICEGATE token.

## 2. Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness probe - does not call ICEGATE. |
| GET | `/api/icegate/health` | Reports which ICEGATE endpoints are configured/confirmed. |
| POST | `/api/icegate/inbound/upload` | Submit an SCMTR JSON file; returns ICEGATE's `uniqueId`. |
| POST | `/api/icegate/ack` | Retrieve the acknowledgement for a previously submitted `uniqueId`. |
| POST | `/api/icegate/outbound/zip-ack` | Retrieve a batched ZIP acknowledgement. |

All responses use the standard envelope:

```json
{
  "success": true,
  "statusCode": 200,
  "message": "File submitted successfully.",
  "errorMessage": null,
  "correlationId": "CORR-20260904-000001",
  "data": { }
}
```

`success: false` means either a request validation failure on our side (HTTP 400) or an
ICEGATE business validation failure (HTTP 422/403/etc.) - `errorMessage` always preserves
ICEGATE's original wording when the failure originated at ICEGATE. `data: null` on failure.

A 202 response from `/api/icegate/ack` is not a failure - it means the ACK has not yet been
generated by ICEGATE. Retry after a delay (see the legacy client's polling loop in
`legacy-client/IcegateLegacyClient/Program.cs`).

## 3. Authentication

Every call (except `/health` and Swagger) requires the header:

```
X-API-KEY: <internal-api-key-for-this-application>
```

This key is provisioned separately per consuming application/environment via
`InternalApi:ApiKeys` in our API's configuration (secret storage in shared/production
environments). It is **not** the ICEGATE API key.

## 4. Uploading an SCMTR file

```
POST /api/icegate/inbound/upload
Content-Type: multipart/form-data
X-API-KEY: <key>

file = <scmtr.json>
localReferenceNo = <optional, your own tracking id>
icegateId = <optional>
senderId = <optional>
```

Success (`data`):

```json
{ "validationStatus": "SUCCESS", "uniqueId": "123456789ASOCUCHE01" }
```

Persist `uniqueId` against your local filing record - it is required for the ACK call and is
the durable link back to ICEGATE's processing of that filing. A successful HTTP 200 here means
ICEGATE *accepted the file for processing* - it does **not** mean the filing is fully
processed; only the subsequent ACK confirms that.

## 5. Retrieving the acknowledgement

```
POST /api/icegate/ack
Content-Type: application/json
X-API-KEY: <key>

{ "senderId": "SRAVANCFS", "uniqueId": "123456789ASOCUCHE01" }
```

- HTTP 200 -> ACK available; `data.fileName`/`data.filePath` identify where our API stored the
  ACK file on disk (`FileStorage:AckPath`). Fetch/display/store it per your application's needs
  (this API does not currently expose a "download ACK bytes" endpoint - add one if the legacy
  application needs the raw file, backed by `data.filePath`).
- HTTP 202 -> not yet available. Poll again after a delay (do not tight-loop).
- HTTP 4xx/5xx -> a genuine failure; do not retry business validation failures (4xx)
  automatically.

## 6. Retrieving the ZIP acknowledgement

```
POST /api/icegate/outbound/zip-ack
Content-Type: application/json
X-API-KEY: <key>

{ "icegateId": "INMAAISLP1", "messageId": "CUCHE01", "custodianCode": "INMAAISLP1", "batchSize": 50 }
```

`batchSize` must be 1-50. Response `data` gives `fileCount`, `responseId`,
`responseDesc`, and the stored ZIP file's name/path - not the raw ZIP bytes, to avoid a very
large Base64 payload over the wire.

## 7. Error handling contract

| HTTP status | Meaning | Retry? |
|---|---|---|
| 400 | Our own request validation failed (missing field, bad file, invalid batchSize) | No - fix the request |
| 401 | Internal API key missing/invalid, or (rarer) ICEGATE authentication failed after our internal retry-once | No |
| 202 | ACK not yet available | Yes, after a delay |
| 422 / 403 / 404 / 409 | ICEGATE business validation failure | **No** - the request as sent will never succeed |
| 429 / 502 / 503 / 504 | Transient - our API already applies a controlled retry internally before surfacing this | Optional, with backoff, at the caller's discretion |
| 500 | Unexpected internal error | Contact support; safe to retry once, do not loop |

## 8. Correlation IDs

Every response carries a `correlationId`. Send `X-Correlation-Id` on your request to control
the value (useful for tracing a single filing end-to-end across your own logs and ours);
otherwise our API generates one (`CORR-yyyyMMdd-XXXXXX`) and echoes it back in both the
response body and the `X-Correlation-Id` response header.

## 9. Reference client code

See `legacy-client/IcegateLegacyClient/` for a complete, compilable .NET Framework 4.0 client
(`HttpWebRequest`-based, no `async`/`await`) implementing the upload -> save uniqueId ->
poll ACK -> save ACK flow end-to-end, plus `legacy-client/README.md` for how to integrate it
into a real ASP.NET Web Forms/MVC application rather than the console demo shown there.

## 10. Swagger

Full request/response schemas, including the multipart upload form and the `X-API-KEY`
security requirement, are published at `/swagger` when the API runs in the `Development`
ASP.NET Core environment. Do not enable Swagger UI on a production deployment reachable from
outside your internal network.
